# 改进与优化方案(阶段性:先方案 → 定结论 → 再执行)

> 目的:在**动手改代码/跑测试之前**,先把"哪些方案真能提升可观测效能、哪些是白费资源"分析清楚,得到一个
> 合理的阶段性结论,据此决定执行顺序,省时省资源。全部结论基于本轮**实测证据**。

---

## 1. 阶段性结论(当前已知,实测支撑)

**已证明的效能(可写进论文):**
- **S3 请求整合**:平均少用 **18% decode GPU**(1.64 vs 2.0,t=−11.7)、省 **26% decode-GPU·s**(t=−8.9),makespan 不降反快、p95 最低。最强、最无争议。
- **S2 正确性/弹性**:quiesce 后 **100% valid、0 丢失**,亚秒(~0.97s)无损角色切换,6/6 触发。
- **拓扑弹性扩容**:2P2D vs 1P1D,makespan **−31%**(t=−8.8)。

**尚未显现的效能:** S2 / mixed 的 **batch-time(墙钟)收益**。

**根因(本轮实测澄清,推翻了早前"传输受限"的说法):**
- ❌ **不是传输**:`ucx_perftest` 实测 GPU 显存经 UCX-TCP = **2.9 GB/s**(iperf 主机 TCP 3.76 GB/s;NVLink P2P 48 GB/s 可用但被单卡 pod 隔离)。传输**不是**堵点;早前 ~40 MB/s 系坏 UCX 时期的旧值。
- ✅ **是负载结构**:makespan 被 **decode 长尾主导(~75%)**,prefill 只占 ~20% 且与 decode **时间重叠**。于是:
  1. D→P 的触发条件(`prefill 积压 且 decode 空闲`)只在开局一瞬间成立 → 窗口太窄;
  2. D→P 是"拿一个 decoder 换一个 prefill",在 **decode-heavy** 负载上是**零和甚至略亏**(实测 s2 +12%,n.s.);
  3. 单看总 makespan,机制的净收益被长尾淹没,**测不出来**。

## 2. 可提升"可观测效能"的方案分析(按性价比排序)

### 方案 A —— 优化测试负载策略(推荐,低成本、高价值,首选执行)
**做什么**:把负载从"短 prompt、全量一次投放"改成**"长 prompt + 整形到达分段"**,并**分段测服务时间**。
- **长 prompt(1.5–3k token)**:让 prefill 成为 makespan 主导,D→P 才有可观测空间(现在传输已证明够快,长 prompt 的 KV 传输只几十毫秒,可放心用)。
- **整形到达分三段(靠到达时间分,不靠 gate)**:
  - ① prefill 突发(长 prompt + 短输出,同时投放)→ 造"prefill 积压 + decode 空闲" → 逼出 **D→P**;
  - ② 集中 decode(中 prompt + 长输出,停止投新)→ 造"decode 积压 + prefill 空闲" → 逼出 **P→D**;
  - ③ 长尾(几条超长 straggler)→ 逼出 **S3**。
- **无 gate**:不插"确认切换成功"的等待 → **每段墙钟 = 纯服务时间,不再有 harness 污染,wall ≈ 逐段 T_batch**。

**为什么有效**:给每个机制**干净的触发窗口 + 可单独测量的段**;归因方式改为"D→P 看①段服务时间、P→D 看②段、S3 看③段 GPU",总 makespan 仅作参考。

**成本**:改 `run_rollout_batch_e2e.py`(加 phased/整形到达模式 + 逐段测量,约 1 天);跑一轮 5 场景(~2–3h)。

### 方案 B —— 启用 RDMA / NVLink(不推荐,已实测排除)
- **证据**:传输实测 2.9 GB/s,**不是堵点**;S2 的问题是负载结构,不是传输。
- **结论**:对 **S2/S3/mixed 的效能没有帮助**;且改造成本高、脆弱(单卡 pod 隔离、消费级 3090 的 P2P/编排冲突)。
- **唯一相关场景**:将来 **worker 跨节点**部署时,1GbE overlay 才成硬瓶颈 → 那时才需要 RDMA。**属于"多节点规模化"议题,不是当前效能议题。** → **现在不做,省时省资源。**

### 方案 C —— S2/S3 决策错峰(针对 mixed,列为第二步)
- mixed 的问题是 S2 的 D→P→D churn 把 makespan 拉长 +26%,吃掉 S3 的省 GPU。
- 改法:让 S2 在"长尾期"不再切回 2P2D,或把 S2/S3 决策统一到一个"当前是 prefill 期 / decode 尾期"的信号上,**错峰**。
- 成本:改 controller 决策逻辑 + 重建 controller 镜像。**建议在方案 A 验证后再做。**

### 方案 D —— 更大 / 数据中心集群(future work)
- 4 卡 + 消费卡限制了所有效应量级;A100/H100+NVSwitch 或多节点 RoCE 上,机制收益(和 RDMA)才充分。记为**后续工作**,当前不投入。

## 3. 推荐测试策略(方案 A 具体化)

- **场景**:5 个不变(baseline_1p1d / static_2p2d / s2_only / s3_only / mixed),等拓扑对照 + 反平衡顺序 + 3 repeats。
- **负载**:长 prompt 突发 → 集中 decode → 长尾;**整形到达分段,无 gate**;跨场景负载完全一致 + 缓存 nonce。
- **测量口径(核心变化)**:
  - **逐段服务时间**:`prefill 段 wall`(看 D→P)、`decode 段 wall`(看 P→D)、`tail 段 wall + decode GPU`(看 S3);
  - **机制证据**:每次切换的时刻/方向/耗时、S3 迁移+缩容时刻、逐段队列深度与 GPU 分配;
  - 保留:质量门(100% valid / 0 timeout)、平均 GPU 数、总 makespan(仅参考)。
- **归因**:D→P → ①段,P→D → ②段,S3 → ③段;**不再用总 makespan 判 S2**。

---

## 4. 预期结果(诚实预测)

- **D→P**:若①段 prefill 够重,预期**①段服务时间下降**(借第 3 个 prefill worker)。受 4 卡限制,幅度可能不大。
- **P→D**:预期**②段 decode 服务时间下降**(借 prefill worker 补 decode)。
- **S3**:③段 GPU 回收(已证,稳)。
- **mixed**:若先做方案 C 错峰 → 组合收益;否则仍有张力。
- **诚实边界**:4 卡上 D→P/P→D 的效应**可能仍不大或不显著**;但这是**最有可能让它们显现**的设计,且**不动硬件**。若这样都测不出可观测收益,则结论升级为"S2 的价值在弹性+正确性,而非本规模下的 batch-time"——同样是可写的结论。

## 5. 阶段性结论与执行建议

| 方案 | 是否执行 | 顺序 | 理由 |
|---|---|---|---|
| **A 测试负载策略优化** | ✅ **执行** | **第 1 步** | 低成本、最可能显现 D→P/P→D 效能,不动硬件 |
| B RDMA/NVLink | ❌ **不执行** | — | 实测传输非堵点,对效能无帮助;仅多节点规模化时才需要 |
| C S2/S3 错峰(mixed) | ⭕ 视 A 结果 | 第 2 步 | 让组合净收益显现;成本中等 |
| D 数据中心集群 | 📌 future work | — | 超出当前资源 |

**一句话结论**:**先只做方案 A(优化测试脚本的负载策略 + 分段服务时间测量),用一次 5 场景测试把 D→P / P→D / S3 的净收益分别测出来;明确不投 RDMA/NVLink(已实测排除),把资源省下来。** A 跑完再决定是否做 C。
