# 方案(待评审)——贴近生产环境的 RL 推理测试

> **状态:仅为方案设计,尚未实现任何内容。** 本文档供你评审。我们达成一致后,我再实现,然后再运行。你设定的目标:尽量贴近真实生产 RL rollout 部署来测试;指标越精确、越真实越好。每一个跨场景的数字都必须**统一测量**(所有场景用同一套量法)且能够诚实归因。

## 0. 相比旧测试改了什么,以及为什么

旧套件把一个 batch 切成三个**带门控的阶段**(`prefill_burst`、`balanced_decode`、`decode_tail`),并在阶段之间插入拓扑**验证等待**。那些等待(只有 `s2_only`/`mixed` 才会付出)造成了 ~90s 的 `wall_s`−`serving_wall_s` 不对称,也逼得我们不得不发明 `serving_wall_s`。此外固定的场景顺序引入了轮内位置混淆(position confound)。

本方案改为:**一个连续的、真实的 rollout batch,端到端统一测量,机制触发由真实生产信号 + 实时 Prometheus 指标驱动,并且事后观测**——在测量窗口内**不做任何在线验证门控**。

**关键的重新认识:** 控制器已经支持的 RL 生命周期信号(`/api/v1/signals/sampling_progress|sampling_done|batch_complete`)**不是测试脚手架**——它们就是真实 RL 训练框架(veRL、OpenRLHF 等)告诉推理层"一次 rollout 开始了 / 快结束了"所用的真实接口。保留它们**更贴近生产**,而不是更不贴近。我们要去掉的,仅仅是那些人为的"确认拓扑切换成功后才继续"的等待。

## 1. 准备工作(测试搭建)

**1.1 固定部署(每个场景完全一致)**
- Dynamo PD 分离部署,`MAX_GPUS=4`,operator 保持在 0(测试自己管理 worker Deployment;已记入 memory)。
- Worker 镜像 `rl-scaling-s2cordon-1`(S2 丢请求修复),控制器 `cordonfix-1`。
- 各场景之间只有*策略开关*不同(S2 开/关,S3 开/关);*拓扑*是唯一的结构性变量,由等拓扑对照组持有(见 §3)。

**1.2 预热(在测量窗口之外)**
- 先扩到该场景的初始拓扑,等到前端真正 model-ready(`/v1/models` + 一次真实 completion 能走通 disagg 路径),再发一个小的预热 batch 并丢弃。
- 理由:第一次冷启动要 4–6 分钟(模型加载 + CUDA graph + NIXL);把它算进去会淹没 T_batch。**预热时间永不计入**——时钟只在确认 ready 之后才开始。这是我们唯一保留的"检查",且它完全位于 T0 之前,因此不会扭曲任何被测指标,也不会在场景之间产生差异。

**1.3 阈值标定(一次性,按集群)**
- 在这套确切的部署上,测量所选 batch 实际产生的队列深度和利用率,并把控制器的 S2/S3 触发阈值设到这个真实工作区间内,使其能自然触发。(按部署标定是正确做法;另一条路——把 batch 放大到越过出厂阈值——会撞上无 RDMA 的传输天花板并导致 timeout。)
- 本步骤产出:一份简短的标定记录,写明测得的区间和所选阈值,使触发既是自然发生的,又有据可查。

**1.4 一份共享 workload,只生成一次(见 §2),每个场景逐字节复用**,每条请求在 token 0 处带一个 nonce,以打掉跨场景的 KV 缓存复用。

## 2. Workload 模型——真实的 RL rollout batch

真实的 RL rollout(面向推理型 LLM 的 GRPO/PPO)会**一次性提交一批生成请求**,并且必须等**全部**完成才能进入训练步——所以关键是这一批的**完工时间(makespan)**,而众所周知的痛点是**完成长度的长右尾**(少数极长的轨迹一直占着 GPU,而其余早已完成)。

我们就精确地建模这一点,作为**一个 batch**(而非三个阶段):

- **规模:** B 条请求以高并发一次性提交(整个 rollout 一起派发,再由调度器排空)——在 1.3 中标定。
- **Prompt 长度分布:** 从真实分布中抽取(均值/离散度在准备阶段确定),但要**加上界**,使每条请求的 KV 传输量落在无 RDMA 的 TCP 预算内(即我们已刻画的传输天花板)。
- **完成长度分布:** 一个**混合分布**——大部分自然 EOS 结束(中等长度),外加**尾部一小撮(~5–10%)**的长 straggler(`ignore_eos`、高 `max_tokens`)。这条尾巴正是 S3 要去合并的对象。
- **到达方式:** 在 T0 一次性派发(可选一个短暂 ramp)——忠实还原训练框架交出一批 rollout 的方式。

这一个 batch 的**生命周期**会自然经历 prefill 密集 → 混合 → 纯长尾,这正是旧的三阶段所模拟的东西。现在机制是对**真实**演化做出反应,而不是对脚本写死的阶段边界。

**待你评审的开放项(2.A):** 你是否有来自真实 RL 运行的完成长度统计想让我对齐?还是我使用一个有据可依的合成长尾(例如 lognormal 主体 + 固定的 straggler 比例)?这个分布的真实度,是决定结果贴不贴近真实的最大杠杆。

## 3. 场景与混淆控制

仍是五个场景,保留等拓扑对照组(对诚实归因至关重要):

| 场景 | 拓扑 | S2 | S3 | 作用 |
|---|---|---|---|---|
| `baseline_1p1d` | 1P1D | 关 | 关 | 最小资源参照 |
| `static_2p2d` | 2P2D | 关 | 关 | **等拓扑对照组** |
| `s2_only` | 2P2D | 开 | 关 | 隔离 S2 |
| `s3_only` | 2P2D | 关 | 开 | 隔离 S3 |
| `mixed` | 2P2D | 开 | 开 | 组合 |

混淆控制(三者缺一不可):
- **轮次为主的交错(round-major interleaving)**——每一轮把五个场景各跑一次 → 抵消*轮间*漂移。
- **每轮内对场景顺序做平衡(counterbalance,拉丁方/轮换)**,使没有任何场景总是落在最冷的槽位 → **修复轮内位置混淆**(它正是让第 2 轮 wall 数字失效的原因)。
- **≥3 次重复**(如时间允许我建议 5 次,因为 n=3 偏薄)。
- workload 完全一致 + 缓存 nonce;分析采用**轮内配对(paired within-round)**。

## 4. 触发与执行(测量窗口内无门控)

- **T0:** batch 派发到前端(在 1.2 预热之后,不计入时钟)。
- 测试**模拟 RL 训练框架**:发送真实信号(派发时 `sampling_progress`,batch 排空时 `sampling_done`/`batch_complete`)——与生产训练框架发的调用相同。
- **控制器自主地**把这些信号与实时 Prometheus 指标(`dynamo_frontend_queued_requests{role}`、`dynamo_worker_gpu_utilization{role}`、worker 在飞请求数)结合起来,决定 S1/S2/S3 动作。我们**不**阻塞、不轮询确认、不在动作之间暂停。
- **T_end:** 该 batch 的最后一条请求完成。
- T0 与 T_end 之间纯粹是服务 + 并发的自主控制。切换/合并均在**事后**从控制器决策日志和连续采样器(§5)中读取,绝不用在线等待。

## 5. 运行期数据收集

从 T0 到 T_end(再加一小段收尾窗口以捕获缩容 settle)连续采样,全部对齐到同一时钟:

1. **每请求记录**(来自压测驱动):提交时刻、首 token 时刻、完成时刻、prompt_tokens、completion_tokens、状态、由哪个 worker 服务。
2. **GPU 分配时间线**(pod sampler):prefill/decode 的 ready + desired(`spec`)副本数,采样约 1s(在 kubectl 允许范围内尽量快),在*完整*窗口上积分(即已修好的全窗口积分)。
3. **集群指标时间线**(控制器 `/api/v1/status` + 直接 Prometheus):prefill/decode 队列深度、prefill/decode GPU 利用率、worker 状态。
4. **控制器决策日志**:每次 S2 切换(方向、触发原因、耗时、是否丢请求)和 S3 动作(migrate → drain → 缩容、各段耗时、释放的 GPU),均带时间戳——这是权威的机制证据。
5. **DCGM GPU 利用率**(若可用,见 5.A)——最贴近生产真实的利用率信号。

**待你评审的开放项(5.A):** 当 `dynamo_worker_gpu_utilization` 读到 0 时,控制器会回退到"在飞数/容量"的*代理值*,这暗示本集群上可能并未采集真实的每卡 DCGM 利用率。若要一个真正"真实"的 U_GPU,我会在准备阶段核实/启用 DCGM 采集;若不可用,则回退到基于吞吐/容量的代理值并**明确标注**。

## 6. 指标——定义、含义,以及我们实际使用哪些

分层。**只有 Tier 1–3 作为结果上报;** 其余为诊断用途。

### Tier 1 —— 主要产出(论文目标)
| 指标 | 定义 | 单位 | 为什么 | 跨场景可比? |
|---|---|---|---|---|
| **T_batch(makespan)** | T_end − T0,所有场景统一 | s | RL 的目标:更快跑完 rollout | ✅ 现在统一(无场景专属门控)——**它彻底取代 wall_s/serving_wall_s** |
| **GPU-hours** = ∫ 已分配 GPU dt | 在 [T0,T_end] 上对 *desired* 副本数做全窗口积分,拆成 **prefill-GPU-s** / **decode-GPU-s** | GPU·s | 成本目标;S3 的收益就体现在这里 | ✅ desired 副本积分无滞后;用测量对测量、配对 |
| **U_GPU** | 有效 GPU 时间 ÷ 已分配 GPU 时间(有 DCGM 用 DCGM,否则用吞吐/容量代理) | % | 展示 S3 在长尾中移除*空闲* decode GPU | ✅ 带 5.A 注记 |

### Tier 2 —— 质量门(不过则一切不可解释)
`valid_decode_pct`(所有请求正确且完整)、`timeout_count`、`http_5xx_count`。门槛:100% / 0 / 0。

### Tier 3 —— 机制证据(与顺序无关;核心贡献)
S2:切换次数、方向、耗时、**切换期间丢请求数**(=0 即 S2 正确性结果)。S3:迁移数、drain 数、**释放的 GPU** + 时序。

### Tier 4 —— 效率比(上下文)
`tokens_per_GPU_s`、`requests_per_GPU_s` = 每张已分配 GPU 的吞吐。

### Tier 5 —— 仅诊断(不做跨场景结论)
时延分位数、逐窗口利用率曲线、队列深度曲线。

### 明确弃用
- `wall_s` / `serving_wall_s` / `orchestration_overhead_s` —— 这个拆分只因门控设计而存在;T_batch(统一)取代这三者。
- 解析式反事实 `tail_decode_gpu_s_saved` —— 用测量对测量的配对 reclaim 取代。

**数据策略(我们将基于哪些数字做分析):**
1. 先过 Tier 2 门。任一场景不过,则停下、修复、重跑(你的既定规则)。
2. 主打目标指标:**T_batch**、**decode-GPU-hours reclaim**、**U_GPU**——每个都相对 `static_2p2d` 做轮内配对,并跨平衡后的多次重复。
3. 用 Tier 3 机制证据佐证(物理上到底发生了什么)。
4. 报告拓扑效应(`static_2p2d` vs `baseline_1p1d`)作为合理性锚点。
5. 若某指标的轮内配对方差仍然盖过效应,则如实报告为"无显著效应",绝不粉饰。

## 7. 预期结果(诚实的预测)

先把话说在前面,以确保我们是在**测量**而非**钓鱼**:

- **质量:** 100% 有效,0 timeout(两个机制均已验证)。
- **拓扑(2p2d vs 1p1d):** 2P2D 的 T_batch 明显更低(并行度更高)——这是"本套件能测出真实效应"的合理性检查。
- **S3:** **decode-GPU-hours 明显更低**(在长尾释放一张 decode GPU;第 2 轮在尾部窗口测得 ~22%——预计在全 batch makespan 上保持或增大)且**长尾中 U_GPU 更高**;**T_batch 大致持平**(合并不应拉长 batch)。这是预期中的强结果。
- **S2:** 在本集群上 **T_batch 很可能持平**——prefill 是传输受限(已证:~19.5s 墙钟 vs 6.2s 计算),所以在这里增加 prefill 算力无法缩短 batch。S2 可展示的结果是**无损的、亚 2 秒的弹性再平衡**(Tier 3),外加可能的少量 decode 侧效应。我们预测 T_batch 持平并如实报告——S2 的贡献是弹性 + 正确性,它会在 RDMA/更大集群上展现 T_batch 收益。
- **Mixed:** S3 的 GPU reclaim + S2 的再平衡,且不丢请求。

若现实与这些预测不符,那本身就是发现——我们照直报告。

## 8. 风险 / 局限(物理约束不变)
- 无 RDMA + 4 卡 → 传输天花板,效应量级受限;这正是 S2 在此无法展现 T_batch 收益的原因。
- 自然触发依赖 1.3 的标定;若某场景中机制未触发,如实报告,绝不用人造信号强行触发。
- n 偏小;connector(NIXL-pull)路径不可用 → S3 走 recompute(成本上界);S1 planner 仍未被真正驱动。
