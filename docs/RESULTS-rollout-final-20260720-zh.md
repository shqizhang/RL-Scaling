# 生产贴真 RL-rollout 最终数据对比与效能分析（2026-07-20）

> 目的：用**已核实**的最新测试数据,分场景证明 S2 / S3 / S2+S3 组合的效能。分析口径参照
> `RESULTS-four-scenario-20260714-zh.md`(S2 看时间、S3 看 GPU、mixed 看组合),但测量方式已升级为
> **单一连续 rollout batch + 统一 makespan(T_batch)+ 等拓扑对照组 + 轮内配对**(见
> `PLAN-production-faithful-test-2026-07-zh.md`)。

---

## 0. 数据来源与核实声明

本报告使用两套 rollout 套件,**每个数字都从各 run 的原始 `summary.json` 独立重算核对**(不信任中间汇总):

| 套件 | worker 镜像 | controller 镜像 | 完整度 | 用途 |
|---|---|---|---|---|
| **163501** | `s2cordon-1` | `idlerelease-1`(mixed 修复) | 15/15,每场景 n=3 | **性能主数据**(拓扑/S3/mixed) |
| **204503** | `s2quiesce-1`(S2 quiesce 修复) | `idlerelease-1` | 12/15(base/static/mixed 各 n=2) | **S2 正确性确认** + 交叉验证 |

两套的 S3/拓扑/mixed 性能数字一致;204503 额外确认了 S2 质量修复。缺的 3 个 run 是集群基础设施问题
所致(Dynamo operator 半夜被拉回 1 副本,持续把 worker 扩容还原成 0,导致 2P2D 起不来——已定位并压回
0),**与策略/数据正确性无关**。

工作负载(两套完全一致,逐字节复用):一个连续 rollout batch = 96 请求(93 条自然 EOS 短请求
64–256 tok + 3 条 7000-tok 长尾 straggler),并发 48,统一测 `T_batch = 最后一条完成 − 派发`;场景顺序
轮内反平衡(rotation);相对等拓扑对照 `static_2p2d` 做**轮内配对**。

## 1. 质量门:S2 丢请求已彻底修复

| 场景(s2_only) | 镜像 | valid% | 5xx | 结论 |
|---|---|---|---|---|
| 163501 | s2cordon(固定 0.5s settle) | 97.6 | 7 | 高并发下切换瞬间仍丢 7 个 |
| **204503** | **s2quiesce(静默握手)** | **100.0(3/3)** | **0** | **切换瞬间丢请求已消除** |

**修复本质**:把"撤 ModelCard 后固定等 0.5s"换成**静默握手**——撤卡后先排空到 idle,再确认引擎
**连续 1.5s 无新请求到达**(证明前端已把路由管线排空到本 worker)才 sleep;期间任何迟到请求会重新排空
再确认。这关掉了并发 48 下"drain 返回 idle 后、sleep 前仍有请求挤进来被打 500"的竞态。17/17 单测通过。

两套全部 15+12 个 run:**除 163501 那 1 个 s2 run 外,全部 100% valid、0 timeout**。

## 2. S2(关注:正确性 + 墙钟时间)

| 指标(vs 等拓扑对照 static_2p2d,n=3) | 差值 | 显著性 |
|---|---|---|
| T_batch | **+6.99s(+12.3%)** | t=+1.87,**n.s.** |
| decode GPU·s | +14.0(+12.3%) | n.s. |
| 平均 decode GPU | 2.00 vs 2.00(±0） | 无变化 |
| 切换动作 | 6/6 执行,**~968–994ms/次** | 100% valid(quiesce 后) |

- **S2 在本集群不带来墙钟收益**(相对等拓扑对照,+12% 且不显著)。原因:本集群**无 RDMA**,prefill 阶段
  是**传输受限**(KV 走 TCP overlay),不是算力受限——D→P 多借一个 prefill worker 加的是算力,而算力不是
  瓶颈,所以缩不动 makespan。
- **S2 的真正效能是"无损弹性"**:6/6 次亚秒级(~0.97s)原地角色切换,quiesce 后**零请求丢失**。它证明的是
  "可以在忙时把 decode GPU 动态借成 prefill、闲时切回",这个**能力**成立且正确;它在**有 RDMA / 更大集群**
  上才会转化为墙钟收益。

> **与 20260714 报告的关键对齐**:那份报告说"S2 让 serving_wall −26%",是 **s2_only(2P2D) 对比
> baseline(1P1D)**,其改善主要来自 **1P1D→2P2D 拓扑翻倍(2 卡→4 卡)**,而非 D→P 切换本身。本轮用
> **等拓扑对照**把两者分开:拓扑翻倍的收益仍在(见 §5,−31% makespan,与 −26% 一致),而角色切换的**净
> 贡献 ≈0**。两份数据其实一致,本轮只是更严谨地归了因。

## 3. S3(关注:GPU 利用率 / 平均 GPU 数量)——最干净的效能证明

| 指标(vs 等拓扑对照,n=3) | s3_only | 对照 | 差值 | 显著性 |
|---|---|---|---|---|
| **平均 decode GPU** | **1.64** | 2.00 | **−0.36(−18.2%)** | **t=−11.7 显著** |
| **decode GPU·s** | 84.1 | 113.7 | **−29.7(−26.1%)** | **t=−8.9 显著** |
| 总 GPU·s | 186.9 | 227.5 | −40.5(−17.8%) | t=−4.8 显著 |
| T_batch | 51.4 | 56.9 | **−5.4(−9.6%,不升反降)** | t=−2.1,n.s. |
| p95 时延 | **16.0s** | 21.5s | 四场景最低 | — |
| 迁移→排空→缩容 | **3/3 migrated + 缩容 decode 2→1** | — | — | 自主 |

- **S3 真实回收 1 块 decode GPU**:长尾阶段把零散 straggler 整合到更少 decoder,`min_spec_decode` 2→1,
  **平均只占 1.64 块 decode GPU / 3.64 块总 GPU**(对照全程 2 / 4)。这正是 20260714 报告里
  `avg_ready_workers 3.70` 的复现(本轮 3.64,更干净)。
- **省 GPU 且不牺牲时间**:makespan **不升反略降(−9.6%)**、p95 时延**四场景最低**、被迁移请求以 recompute
  透明续跑、100% valid、0 timeout。
- **这是本方案最强、最无争议的效能点**:−26% decode-GPU·s(t=−8.9)、平均少用 18% decode GPU(t=−11.7),
  两套数据(163501 与 204503 的 −19.7%/−17.0%)一致。

## 4. Mixed(S2+S3 组合):协同修复已生效,但本集群有固有张力

**修复确认**:上一轮 mixed 因 S2 的 D→P→D 把长尾全挤到一个 decoder、留下一个空 decoder(3+0 分布),而
旧 S3 逻辑对"空 decoder(0 在飞)直接跳过",导致 **S3 在 mixed 里从不触发**。本轮加入**空闲 decoder 免迁移
释放**(`is_release`)后:

| 指标(mixed,n=3) | 值 | 说明 |
|---|---|---|
| 平均 decode GPU | **1.85 vs 2.00(−7.5%,t=−3.8 显著)** | **S3 现在会触发**、缩容 2→1 ✅ |
| S3 缩容证据 | drained + `min_dec=1`(6 次) | 修复生效 |
| S2 切换 | 6/6,~994ms,100% valid | S2 正常 |
| **T_batch** | **71.8 vs 56.9(+26.3%,t=+18.4 显著)** | ⚠️ S2 churn 拉长了 batch |
| decode GPU·s | 132.8 vs 113.7(**+16.7%**) | ⚠️ 净 GPU·s 反而更高 |

- **组合的机制都成立**:S2 无损切换 + S3 缩容释放 GPU 都在 mixed 里正确发生。
- **但净收益被本集群的传输瓶颈吃掉**:`decode GPU·s = 平均 decode GPU × T_batch`。mixed 平均 GPU 虽降到
  1.85(<2.0),但 S2 的角色 churn(D→P 期间只剩 1 decoder、P→D 再加回)把 makespan 拉长 26%,于是
  **积分出来的总 GPU·s 反而更高**。这正是 20260714 报告预判的"一个往上弹、一个往下弹的固有张力"。
- **诚实结论**:在**无 RDMA 的 4 卡集群**上,S2 帮不动时间、只添 churn,所以 S2+S3 的**净**效益不如 S3 单独。
  组合的价值要在 S2 能真正缩短 prefill 的环境(RDMA/更大集群)才显现;当前可作为"机制可组合、且组合后仍
  无副作用(100% valid)"的证据,而非"净收益叠加"的证据。**下一步建议**:让 S2/S3 决策错峰,或 S2 在纯长尾
  阶段不再切回 2P2D。

## 5. 拓扑锚点(基础扩缩容能力):2P2D vs 1P1D

| 指标(static_2p2d vs baseline_1p1d,n=3) | 差值 | 显著性 |
|---|---|---|
| **T_batch** | **−25.6s(−31.0%)** | **t=−8.8 显著** |
| 总 GPU·s | +62.5(+37.9%) | 显著(2 卡→4 卡换速度) |

- 这证明**最基础的弹性扩缩容能力成立**:把拓扑从 1P1D 扩到 2P2D,同一批 rollout 快 **31%** 完成(代价是
  用了 2 倍 GPU·s——延迟/吞吐的经典权衡,而 S3 正是把这多用的 GPU·s 再回收一部分)。
- 也回应了 20260714 那份 −26% 的来源:那 −26% 主要就是这个拓扑翻倍效应。

## 6. 整体效能结论

| 维度 | baseline(1P1D) | S2 | S3 | Mixed(S2+S3) |
|---|---|---|---|---|
| 质量(valid%) | 100 | **100(quiesce 修复后)** | 100 | 100 |
| T_batch(makespan) | 82.5s | 63.8s（+12% vs 对照,n.s.） | **51.4s（−9.6%,四场景最快）** | 71.8s（+26%,张力） |
| 平均 decode GPU | 1.0 | 2.0 | **1.64（−18%,t=−11.7）** | 1.85（−7.5%,t=−3.8） |
| decode GPU·s | 82.5 | 127.7 | **84.1（−26%,t=−8.9）** | 132.8（净增,张力） |
| p95 时延 | 26.7s | 23.7s | **16.0s（最低）** | 26.8s |
| 机制动作 | — | 6/6 切换 ~0.97s 无损 | 3/3 迁移+缩容 2→1 | 6/6 切换 + 缩容 2→1 |

**逐方案效能判定:**
- **S1 弹性扩缩容**:✅ 成立(2P2D 比 1P1D 快 31%,显著)。
- **S2 角色切换**:✅ **正确性**成立(quiesce 后 100% valid、亚秒切换);⚠️ 本集群**无墙钟净收益**(传输受限,
  非机制缺陷)。效能 = 无损弹性能力。
- **S3 请求整合**:✅✅ **最强效能**——平均少用 18% decode GPU、省 26% decode-GPU·s,且 makespan 不降反快、
  p95 最低,高度显著,两套数据一致。
- **Mixed 组合**:✅ 协同已修复(S3 在 S2 存在时也能触发缩容);⚠️ 本集群净 GPU·s 被 S2 的 makespan 惩罚
  抵消——机制可组合、无副作用,但净收益需 RDMA 环境才显现。

## 7. 局限与威胁

- **无 RDMA + 4 卡**:是 S2 无墙钟收益、S3 回收量有界、mixed 张力的**根因**——集群互连特性,非机制缺陷。
- **样本量**:S3 的大效应(t≈−9 到 −12)与质量/机制结论稳健;小效应(S2、mixed 墙钟)n=2~3 偏薄。
- **基础设施波动**:Dynamo operator 若被拉回 1 副本会持续还原 worker 扩容(本轮 3 个 run 缺失的根因,已定位),
  需保证 operator=0;worker 冷启动偶发 vLLM engine-core 崩溃(已加 prewarm 重试 + 套件可续跑)。
- **TTFT 未采集**(压测路径非流式);`s2_switch_total_ms` 汇总字段有 bug(真实 ~0.97s 从日志取得);U_GPU
  用 KV-cache 占用代理(DCGM 未采集),因 batch 偏小信号弱——GPU 效能以 GPU·s / 平均 GPU 数为主。
